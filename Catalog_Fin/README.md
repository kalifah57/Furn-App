# Furn-App Catalogue Extractor

Extracts real furniture products from Saudi retailers into the exact JSON schema
the Furn-App Spatial Engine and Aesthetic AI Engine consume.

```bash
pip install -r requirements.txt
playwright install chromium          # optional; see "The browser retry"
python -m furn_catalog --limit 50 --out catalog.json -v
```

Output is a JSON array, one object per product:

```json
[
  {
    "id": "s79482824",
    "product_name": "KIVIK 3-seat sofa, Tresund anthracite",
    "store": "IKEA KSA",
    "category": "sofa",
    "price_sar": 2495.0,
    "urls": {
      "product_link": "https://www.ikea.com/sa/en/p/kivik-3-seat-sofa-tresund-anthracite-s79482824/",
      "image_url": "https://www.ikea.com/sa/en/images/products/kivik-3-seat-sofa__1103001_pe867123_s5.jpg",
      "3d_model_url": "https://api.furn-app.com/assets/models/kivik_3_seat_sofa_s79482824.usdz"
    },
    "spatial_attributes": {
      "length_cm": 95.0,
      "width_cm": 228.0,
      "height_cm": 83.0
    },
    "aesthetic_features": {
      "primary_colors": ["Dark Grey"],
      "material": "Polyester fabric, solid pine",
      "style": "Contemporary Dark",
      "vibe": "Grounded, masculine, cosy, practical"
    }
  }
]
```

## The output contract

Every record has an identical key set, in an identical order, with identical
types. A Dart model can deserialise it without a single null-check or
`containsKey`, which is the whole point:

| Guarantee | Why it is a guarantee and not a habit |
| --- | --- |
| `spatial_attributes` is exactly three axes | The `PlacementSolver` reads this and nothing else. Advisory numbers are kept physically out of reach rather than relying on the solver to ignore them. |
| all numerics are JSON **floats** | `json.dumps` writes `95` for an int; Dart's `jsonDecode` returns `int`, and `data['length_cm'] as double` then throws. Most furniture is a whole number of cm, so ints would crash the common case and work only on the odd 83.5cm chair. |
| `aesthetic_features` always has all four keys | Values may be `""` / `[]` when nothing could be read; the keys never disappear, so the Aesthetic engine reads unconditionally. |
| `id` is the retailer's article number | Stable primary key for the DB and the Riverpod store. Never empty — a record without one fails validation. |
| `price_sar` is a float or `null` | `null` means *not found*. It is never `0.0`, because a free sofa is a different claim from an unknown price. Use `--require-price` to drop those records instead. |

### Discovery is round-robin, not first-come

Queries are interleaved — the first result of every query, then the second of
every query — and no more than two fabric variants of one model are taken
before the rest are deferred (`--max-variants`, `0` disables it).

Both exist because three consecutive live runs came back ~94% sofas. Not
because IKEA has nothing else: discovery drained `sofa`, `3-seat sofa` and
`corner sofa` in order, and those three returned more products than the whole
run needed, so it stopped before ever asking about desks or wardrobes. IKEA also
lists each sofa once per cover, so four EKTORPs arrived before a second model —
and four colours of one sofa are a single footprint to the solver. On a
simulated 20-product run the two changes together take distinct models from 6
to 15.

`--schema extended` adds what the pipeline can also resolve — `room_category`,
`depth_cm` (the same axis as `length_cm` under the retailer's naming),
`seat_depth_cm`, `texture`, `pairs_with`, and a `data_quality` block on a
flagged record. It is opt-in specifically so the strict shape above cannot
drift as a side effect of the scraper learning something new.

Verify any catalogue against the contract in one command:

```bash
python -m furn_catalog.validate catalog.json --expect 50
```

## Published contract

Furn-App consumes this repository directly. **One catalogue per retailer**, each
with its own manifest, at fixed locations that never move — consumers hard-code
these raw URLs:

```
https://raw.githubusercontent.com/abdulazizashy4/Catalog/main/catalog.json
https://raw.githubusercontent.com/abdulazizashy4/Catalog/main/catalog.manifest.json

https://raw.githubusercontent.com/abdulazizashy4/Catalog/main/catalog.homecentre.json
https://raw.githubusercontent.com/abdulazizashy4/Catalog/main/catalog.homecentre.manifest.json
```

`catalog.json` is **IKEA KSA**. It keeps the unqualified name because Furn-App
already points at it; renaming it to `catalog.ikea.json` would break a consumer
to gain nothing but symmetry. Every retailer added after it is qualified.

Each file is generated by its own run and versioned independently, so a
retailer whose markup breaks does not take the others down with it:

```bash
python -m furn_catalog --retailer ikea:50       --out catalog.json            --render always
python -m furn_catalog --retailer homecentre:50 --out catalog.homecentre.json --render always
```

`catalog.manifest.json` is how a consumer detects change cheaply — it polls a
few hundred bytes and pulls the catalogue only when `sha256` differs:

```json
{
  "schema_version": 1,
  "record_count": 50,
  "sha256": "83e17aa4bf648e80adc1c1de6b6be893fdebb2d8efca3955d788ae05dd5b4dc9",
  "generated_at": "2026-08-10T06:04:32Z"
}
```

It is **generated, never hand-written**. `python -m furn_catalog --out catalog.json`
writes it from the bytes it just wrote and re-verifies both files agree; a
mismatch fails the run with exit code 2. A hand-maintained hash drifts, and a
drifted hash either pins the consumer to a stale catalogue forever or makes it
re-download an unchanged one on every poll — neither raises anything anywhere.

### This repo publishes raw

Validation belongs to the consumer, and duplicating it here would be worse than
useless: Furn-App's ingestion layer is tested against specific bad records, so
pre-dropping them upstream makes its own drop counts meaningless.

So records that *look* wrong still ship — the NEIDEN bed with an 8 cm height,
the two HÄGERNÄS sets at 1.2 × 40 × 4, the transposed LACK and SANDSBERG. The
category extent floors still run, and the run report names them:

```
  suspect   : 3 emitted with a component-sized axis (published raw; the consumer drops these)
```

`--enforce-extents` turns that back into a drop for anyone publishing to a
consumer that does not validate.

What the pipeline *does* still enforce, because every consumer depends on it, is
the contract itself: the exact key set, float numerics, `price_sar` float-or-null
(never `0`), https `/sa/en/` links, a resolved `id`, and all three axes present.

### Changing the shape

`SCHEMA_VERSION` in `schema.py` is the number in the manifest. Bump it whenever a
key is added, removed or renamed, a unit changes, or an axis changes meaning.

`tests/test_manifest.py` pins the exact published key set to that number, with
the key names written out rather than derived from the code — a test that asks
the code what shape it emits agrees with whatever the code emits, and would
catch nothing. Change the shape and the suite fails until the version is bumped
deliberately. Silent drift is the one failure a downstream consumer cannot
defend against.

### Commit discipline

One commit per regeneration, touching only `catalog.json` and
`catalog.manifest.json`, with the record count and hash in the message. Both are
tracked in git on purpose — they are the deliverable, not build output.

### Instant sync (optional)

`.github/workflows/notify-consumer.yml` sends a `repository_dispatch` of type
`catalog-updated` to `kalifah57/Furn-App` on every push that touches either
file, with the sha256, record count and schema version in `client_payload`.

It is inert until a secret named `FURN_APP_DISPATCH_TOKEN` exists on this repo —
a fine-grained PAT with **Contents: read** and **Metadata: read** on
`kalifah57/Furn-App`. Without it the workflow logs a notice and does nothing;
the manifest poll still works. Nothing here stores a credential.

## Why this is a pipeline and not a data file

The catalogue was requested as 50 finished records. Two of the required fields
cannot be obtained without going to the live retailer:

- **`image_url`** — IKEA CDN paths embed an opaque asset id
  (`__1103001_pe867123_s5.jpg`). It is not derivable from the product name or
  the article number. Any value not read off the source is a guess that 404s.
- **`spatial_attributes`** — the measurements.

Both feed load-bearing systems: a wrong footprint makes the PlacementSolver
place furniture that does not physically fit, and a dead image URL breaks the
product card. Both fail *silently*, deep in the app. So this repo ships the
extractor rather than hand-written records.

Run it from any network that can reach the retailers and you get the 50 items.

## Where the data actually comes from

The first live run made this concrete, and it is worth stating plainly because
the obvious answer is wrong: **IKEA product pages do not carry their own
measurements.** Of 102 candidates visited, 54 parsed cleanly for name and image
and yielded no dimensions at all — not from the measurement block, not from a
whole-page sweep for `Width: … cm`. The measurement block is rendered
client-side, so no selector reaches it. A further 47 candidates 404'd outright,
because IKEA KSA does not resolve a product by its trailing article number when
the URL slug is from another market; it just returns 404.

So `sik.search.blue.cdtapps.com` — the backend ikea.com's own search box calls
— is the discovery source: per product it returns the canonical `/sa/en/`
`pipUrl` and the CDN `mainImageUrl`. That part is confirmed against a live
response.

**The measurement field is not.** The design assumed the same response also
carries `itemMeasureReferenceText`. A live check against the real endpoint
found the opposite: 12 real sofas returned with correct names and URLs, every
one with an empty measurement field, on the exact query the pipeline itself
sends. Either this endpoint genuinely does not carry dimensions (a lean
search/typeahead index has no obvious reason to), or the field is nested one
level deeper than the scan reaches — `_measure_text` originally only checked
the product object's own direct string values, not sub-objects, and has since
been widened to scan recursively as a no-downside hardening. Whether that
recovers anything is still unconfirmed; nobody has seen the real JSON shape
yet. Run this to get it:

```bash
python -m furn_catalog.diagnose --raw sofa
```

...and see "Diagnosing an extraction failure" below for how to feed it back in.

Dimensions are taken from the first source that yields a plausible footprint,
and the winner is recorded in each record's provenance so a run can be audited
for how much of it leaned on the weaker fallbacks:

| Order | Source | Notes |
| --- | --- | --- |
| 1 | search API measurement field | structured, when present — **unconfirmed on live data**, see above |
| 2 | embedded JSON in the page | same shape, when a blob survives in the markup |
| 3 | labelled measurement block | the classic `dl`/`dt`/`dd` path |
| 4 | labelled text in the description | `Width: 228 cm, Depth: 95 cm` |
| 5 | title triple | `KOPPANG … 90x46x83 cm` |
| 6 | any `WxDxH cm` in the raw markup | last resort, cannot tell a footprint from an unrelated triple |

A live page check (see "The browser retry" below) found sources 2–6 all empty
on real IKEA pages despite the markup containing the substring `cm` **113
times** — those instances are elsewhere on the page (prices, unrelated copy),
not in a parseable triple. That is independent confirmation that the
measurement panel is genuinely client-rendered, which is what source 2–6
failing uniformly across sources of very different mechanisms would predict.

If the API is unreachable the adapter falls back to seeds and listing crawls
and says so in the log — degraded, not broken.

### The browser retry — currently the load-bearing path, not a fallback

Where all six static sources come back empty, the page is re-fetched in
headless Chromium, which clicks open anything that looks like a measurements
panel (English or Arabic labels, `aria-expanded="false"` accordions,
`<details>`) and re-parses the expanded markup.

It was designed as a retry for the occasional page a fast static path misses.
Live evidence changes that framing: on the pages checked so far, *all six*
static sources come back empty, which means this is not covering an edge case
— it is currently the only mechanism that can produce a dimension at all for
IKEA. That makes whether it actually works the single most important open
question in this repository. It has not been run yet in this environment
(Playwright cannot be installed here); the run report's `rendered:` line is the
first real signal:

```
  rendered  : 12 retried in-browser, 9 recovered
```

`recovered` near `retried` means the click-to-expand path works and the design
holds. `recovered` near zero means the panel isn't opening the way this code
expects — wrong selector, wrong wait condition, or a bot-detection response —
and needs a real fix, not another guess.

The first live probe returned exactly that worst case: `40 retried, 0
recovered`. The renderer has since been rebuilt around the failure mode that
survives scrutiny: **`page.content()` serialises only the light DOM**, so if
the panel renders into an open shadow root, every click can land and the
returned HTML still never contains a number. The renderer now serialises the
DOM itself with shadow roots inlined, extracts the *visible* shadow-pierced
text as its own extraction layer (`browser-text`), dismisses the cookie
overlay before clicking (an overlay eats clicks silently), and waits on a
condition — measurement text actually visible — rather than a fixed sleep.
Each record's provenance carries the evidence: clicks landed, whether the wait
fired, and visible cm-token counts before → after expansion.

Whether that rebuild recovers dimensions on live pages is testable in one
command, on one URL, before any scrape:

```bash
python -m furn_catalog.diagnose --render "https://www.ikea.com/sa/en/p/<any-product>/"
```

It prints the click trail, the token counts, every extraction layer against
the rendered DOM, and a one-line VERDICT; the shadow-inclusive markup lands in
`render_dump.html` for direct inspection (grep it for `shadowrootmode`).

Playwright is optional in principle. Right now it is required in practice: a
run without it, in the current state of the static extractors, will emit
approximately nothing for IKEA.

```bash
pip install playwright && playwright install chromium
```

`--render always` opens the measurements panel on **every** product rather than
only where the static parse came up short. Slower — a browser page-load per
product — but the panel is the authoritative source, and a static page can
carry a plausible-looking measurement that is not the bounding box. Use it when
correctness matters more than runtime; `auto` remains the default.

The wait after clicking is a condition, not a sleep: the renderer proceeds once
the count of visible measurement tokens has *grown* past what was on the page
before the click. Testing merely that "a measurement is present" would pass
instantly on a page already showing `Seat depth: 54 cm` statically, and capture
before the panel finished opening — which is one way a component measurement
ends up standing in for a bounding box.

```bash

```

## The dimension mapping (read this before trusting the output)

Retailers publish **Width** (side-to-side), **Depth** (front-to-back), and
**Height**. The Furn-App schema calls the front-to-back axis `length`:

| Retailer field | Furn-App field |
| -------------- | -------------- |
| Depth          | `length_cm`    |
| Width          | `width_cm`     |
| Height         | `height_cm`    |

This matches the KIVIK example in the original spec (IKEA W228 × D95 × H83 →
`length_cm: 95, width_cm: 228, height_cm: 83`). Reversing it rotates every item
90° in the solver, so the mapping lives in exactly one place
(`Dimensions.from_retailer`) and is pinned by a test.

Sub-measurements never become an axis. A sofa's `seat depth` is ~60 cm against a
real depth of ~95 cm; using it would let the solver place the sofa 35 cm too
close to the wall. It is still *carried*, as `seat_depth_cm`, because the
Aesthetic engine wants it — just never anywhere the solver could mistake it for
the footprint.

### Which labels may define the box

This is enforced by a **whitelist**, and the reason is a defect that shipped:
`Armrest width: 3.5 cm` was read as a sofa's width. Two faults compounded. The
free-text parser captured only the bare axis word, discarding the qualifier
before anything could reject it — so `Armrest width` and `Width` arrived
downstream indistinguishable, and first-match-wins took the armrest. And the
filter was a blacklist of known prefixes, which had never heard of "armrest".

A blacklist is only as good as its last update, and a miss here produces a
3.5 cm sofa that passes every plausibility check. So a label now defines an axis
only if it **is** that axis word:

| Accepted | Rejected |
| --- | --- |
| `Width`, `Depth`, `Height`, `Length` | `Armrest width`, `Seat depth`, `Seat height` |
| `Total width`, `Overall height` | `Height under furniture`, `Height backrest` |
| `Height including back cushions` | `Compressed packaging depth`, `Bed width` |
| Arabic equivalents | anything else, including labels not yet invented |

Two refinements the live panels forced:

- Where both a bare axis and an `including …` variant are published, the
  **larger** wins. `Height including back cushions: 84 cm` beats `Height: 78 cm`
  — 84 is what has to clear a doorway.
- A section heading is treated as a boundary, not a prefix. Panel text runs on
  as `… 2-seat sofa Measurements Width: 132 cm`, and stripping only a leading
  heading leaves `sofa` in front of the axis word, where it reads as a qualifier
  and costs the product a width it published plainly.

If the three global axes cannot be isolated, the record is dropped as
`no_dimensions`. A component measurement is never promoted to fill a missing
axis — a sofa reconstructed from its seat is worse than no sofa.

### Packaging is not the product

Extraction is scoped to the measurements panel, from its heading to the next
section heading. That is not tidiness: IKEA labels **package** dimensions with
bare `Width:` / `Height:` / `Length:` — the same words the product uses — and a
flat carton is often longer than the sofa is deep. Reading the whole page and
taking the largest value per axis gave a live EKTORP a depth of **205 cm**, its
carton's length, against a real depth of 88 cm. No rule about labels can catch
that, because the labels are identical; only knowing which section a number came
from can. Pages with no recognisable panel are still truncated at the first
packaging heading.

## Everything is Saudi Arabia, and that is enforced

Each retailer runs one storefront per market, distinguished by a path segment.
Cross-market leakage is easy and completely silent: a seed from `/us/en/`, a
listing page linking to `/ae/en/`, a `<link rel="canonical">` pointing at the
global site — each yields a page that parses perfectly and describes a product
with the wrong price and availability for a Riyadh customer.

`locale.py` holds the rule, and it is applied at both ends:

- every discovered URL is rewritten onto `/sa/en` before it is fetched, and any
  URL belonging to no known Saudi storefront is skipped;
- `product_link` is re-checked at validation, so a record whose link escaped the
  first gate cannot be emitted.

`/sa/ar/` is rewritten too — the Arabic Saudi storefront is still the wrong one,
because the catalogue is English-only.

## Guarantees

Enforced in `schema.py`, applied to every record before it is emitted:

1. **Dimensions are mandatory.** All three axes or the product is dropped — never
   guessed, never partial. Values outside 1–400 cm are rejected as parse errors.
   A page that comes back short is retried in the browser first; only then is it
   dropped. Aesthetic features are deliberately *not* gated this way: an
   unreadable style still leaves a perfectly placeable product, so it ships with
   empty values rather than costing the catalogue a record.
   `--allow-incomplete` (extended schema only) ships a dimensionless record
   instead, carrying a visible flag:

   ```json
   "spatial_attributes": null,
   "data_quality": { "complete": false, "issues": ["missing_dimensions"] }
   ```

   Off by default — the solver cannot place a product with no footprint, so a
   flagged record only helps a consumer that has agreed to read the flag. A
   complete record carries no `data_quality` block at all, so its absence is the
   signal.
2. **English only.** Any Arabic script surviving into a text field fails
   validation rather than shipping mixed-language data.
3. **Real URLs.** `product_link` must be https, must point at a Saudi
   storefront, and must carry a resolved SKU; `image_url` must be an https CDN
   link and is checked against placeholder patterns.
4. **Deduplicated by article number**, so the same product reached via two
   market slugs appears once.
5. **Prices are Saudi or absent.** A price is only read when the source labels
   it SAR. A number carrying AED or USD is discarded rather than written into
   `price_sar`, because a wrong-currency price looks perfectly usable.

Anything dropped is counted and explained in the run report:

```
Run report
----------
  requested : 50
  visited   : 137
  emitted   : 50
  dropped   :
      41  not_a_product_page
            e.g. https://www.ikea.com/sa/en/p/songesand-bed-frame-brown-s89241044/
      12  no_dimensions
            e.g. VIMLE cover only (no published measurements)
```

## Seeds

`seeds/ikea_ksa_seeds.json` holds 67 IKEA article numbers across sofas, beds,
armchairs, dressers, dining tables, desks, bookcases, and shelving.

Every article number was observed in a live IKEA search result. `observed_on`
records which market's URL appeared — six are confirmed on `/sa/en/` directly;
the rest were seen on other markets. **IKEA article numbers are global** (the
MALM high bed frame is `s09929373` on `/sa/`, `/kw/`, and `/se/` alike), so an
article seen elsewhere is a valid *candidate* for KSA.

The file asserts nothing about KSA availability, price, or dimensions. The
pipeline resolves each URL against `/sa/en/`, follows the redirect to the
canonical slug, and drops whatever 404s. Expect a meaningful share to drop —
that is the seed list doing its job, which is why discovery oversamples 3× and
falls back to crawling category listings once seeds are exhausted.

Add seeds for other retailers by appending entries with `"retailer": "abyat"`.

## Aesthetic extraction

`--aesthetics rules` (default) maps the retailer's own colour and material
vocabulary onto the normalised English feature set. Deterministic, offline,
auditable, free to re-run. It never invents a material it cannot read.

`--aesthetics vision` is the literal reading of "act as the AI vision": the real
product image is sent to Claude, which returns the same six fields under a
strict JSON schema. It sees the product rather than inferring from its name, at
the cost of one API call per item. Needs `pip install anthropic` and
`ANTHROPIC_API_KEY`; falls back to the rule-based path on any failure so one bad
call never sinks a run.

## `3d_model_url` is a pointer you own

No retailer publishes USDZ assets. This field is generated deterministically
from the SKU into *your* asset namespace:

```
https://api.furn-app.com/assets/models/{slug}_{sku}.usdz
```

It is a stable address for an asset you will produce, not a scraped fact —
nothing resolves there until you upload one. Change the shape with
`--model-url-template`, which accepts `{slug}`, `{sku}`, and `{category}`.

## Adapter maturity

**Be aware of this before running against Home Centre or Abyat.**

**Default runs are IKEA-only.** Home Centre and Abyat are still shipped and
still selectable, but the first live run established that neither contributes:

| Adapter | Status |
| --- | --- |
| `ikea` | The working path. Search backend for discovery, URLs, images and measurements; product page for materials, price and description; browser retry for the rest. |
| `homecentre` | Same extraction depth as `ikea` — shared label whitelist, packaging scoping, browser-text layer — and verified end-to-end against a local fixture reproducing Landmark's page shape. Discovery runs off the sitemap advertised in `robots.txt`. **The live markup is still unverified**: this environment cannot reach the site. |
| `abyat` | Selectors unvalidated. Discovery moved to the sitemap; the `/sa/en/c/...` paths answered 404 and 202, the 202 being a bot-check interstitial. Browser headers address the interstitial. |

Select them explicitly with `--retailer homecentre:8` if your access differs.
Any quota they fail to fill is topped up from IKEA, so a mixed run still
reaches `--limit`.

### Why sitemaps replaced the category paths

The original hardcoded listing paths scored 0 for 10 on the first live run —
five 404s and five 202 challenge pages. Writing *better* paths buys one more run
before they rot again, so discovery now reads each retailer's own sitemap:
published by the retailer, advertised in `robots.txt`, and updated in the same
deploy that moves a category. The old paths remain as a last-resort fallback.

**I could not verify replacement category URLs for these two.** The authoring
environment has no route to either site, so any path I wrote by hand would be
another guess presented as a fix. The sitemap approach is what removes the need
to guess; if it comes back empty on your network, `-vv` will show which sitemap
was tried.

### Browser headers, and what they do not do

Home Centre and Abyat both answer the honest `FurnAppCatalogBot` User-Agent with
a challenge page, so those two adapters send desktop-Chrome headers instead.
That changes what the scraper *looks* like, not what it *does*: robots.txt is
still fetched and obeyed, evaluated against our own UA, and the rate limit is
unchanged. Nothing a retailer disallowed becomes allowed — there is a test
pinning exactly that. Home Centre's disallowed listings stay disallowed, and
`--ignore-robots` remains the only way past them, for people who have asked.

`-vv` logs every parse decision, and the run report names what fell out.
`_specs()` in `adapters/generic.py` and `spec_selectors` are the two places
likely to need adjustment.

### Auditing the output

```bash
python -m furn_catalog.validate catalog.json --expect 50
```

Checks the *file* rather than the run that produced it, so it also catches a
truncated write, a hand-edit, two runs merged by hand, or schema drift between
the version that wrote the file and the version about to read it. Prints
per-field coverage and exits non-zero on any problem, so it can gate a deploy.

It also applies **category-aware extent floors**, which exist because two
catalogues shipped component measurements past a clean validator run. The flat
1-400cm plausibility gate cannot see anything wrong with `width_cm: 3.5` — it is
a perfectly ordinary number, and only the record's claim to be a *sofa* makes it
impossible. The floors are deliberately loose (a real two-seat sofa is ~130cm
wide; the floor is 90) because they exist to catch a component masquerading as
the bounding box, not to police accuracy. Run against the catalogue that carried
the defect, they flag 33 of 50 records.

### Diagnosing an extraction failure

When a run drops products for `no_dimensions`, this says which layer failed
rather than leaving you to guess:

```bash
python -m furn_catalog.diagnose                      # probe the API, sample 3 products
python -m furn_catalog.diagnose <product-url> ...    # inspect specific pages
python -m furn_catalog.diagnose --raw sofa            # the API's raw JSON, verbatim
```

It prints, per URL, what each of the six sources returned, whether the page was
reachable, and how many times `cm` appears in the raw markup — the fastest tell
for whether a page carries measurements at all. It reads the same on-disk cache
as a real run, so re-diagnosing costs the retailer nothing.

`--raw` exists specifically for the current open question above: it prints the
search API's decoded response with no interpretation, so a mistaken field-name
assumption is visible directly instead of producing another guess.

## Politeness

Scraping a live retail site badly gets you blocked. The client obeys robots.txt,
rate-limits per host (1 req/s + jitter, `--delay` to change), retries only
transient failures with exponential backoff, identifies itself honestly, and
caches every response to disk so re-runs cost the retailer nothing.

robots.txt is fetched and parsed directly rather than via
`RobotFileParser.read()`, to follow RFC 9309 §2.3.1.3 on status codes: a 4xx
means no policy is published and crawling may proceed, while a 5xx means the
host is unwell and is treated as a full disallow. urllib's parser instead reads
401/403 as a blanket ban, which locks you out of hosts that simply never serve a
robots.txt — including IKEA's search backend. Explicit `Disallow` rules are
honoured exactly as written either way; that is why Home Centre's category
listings are skipped rather than scraped.

`--ignore-robots` exists for when you have the site owner's permission. Don't
use it otherwise.

## Layout

```
furn_catalog/
  units.py       cm normalisation, W/D/H → L/W/H mapping     (no dependencies)
  schema.py      the record + the rules that gate it         (no dependencies)
  locale.py      KSA storefront enforcement                  (no dependencies)
  ikea_api.py    IKEA's search backend: URLs, images, sizes  (no bs4)
  sitemap.py     retailer-published product discovery        (no bs4)
  render.py      headless Chromium; opens measurement panels (playwright, optional)
  aesthetics.py  rule-based and Claude-vision extractors
  http.py        polite cached client
  adapters/      base contract, ikea, generic (homecentre/abyat)
  pipeline.py    discover → parse → retry → validate → emit
  cli.py         argument handling and retailer quotas
  diagnose.py    which extraction layer answered, per URL
  validate.py    audit a finished catalogue file
seeds/           candidate article numbers with provenance
tests/           unit + offline end-to-end fixtures
```

`units` and `schema` are dependency-free on purpose, and the package imports the
scraping stack lazily — `from furn_catalog import Dimensions, Product` works
without beautifulsoup4, so a consumer that only validates catalogues doesn't
need the scraper.

## Tests

```bash
pip install pytest && python -m pytest tests/ -q
```

`tests/test_pipeline.py` runs the whole pipeline against fixture pages shaped
like IKEA's real markup — no network — and asserts the drop rules actually drop:
missing dimensions, unavailable articles, duplicate SKUs. `tests/test_ikea_api.py`
pins the search-backend decoder, including that it survives a renamed wrapper
key or measurement field, and that an unparseable measurement yields `None`
rather than a guess.

**Verification status.** The authoring environment has no PyPI access and no
route to the retailers, which bounds what can be claimed here.

*Executed, all passing (177 tests):* the full suite except the live scrape —
locale enforcement, sitemap parsing, price and room extraction, unit conversion
and axis mapping, schema validation, the search-API decoder, the end-to-end
pipeline against fixture pages, and `HttpClient` itself against a throwaway
localhost server (robots semantics, caching, redirects, header profiles).

Two caveats on that number. The bs4-dependent tests were run against a stdlib
stand-in for BeautifulSoup, so they verify the pipeline's *logic* rather than
that the CSS selectors match real markup — run `pytest` against real bs4 before
trusting a scrape. And `render.py` could not be executed at all: Playwright is
not installable here, so its fallback path is tested and its browser path is not.

*Not executed:* a live run. The dry run below cannot be done from here.

Three real bugs have come out of these offline runs, all the same shape — a
wrong or missing value rather than an exception, which is the only kind this
project genuinely fears:

- a trailing-`"` inch measurement fell through to the centimetre default (2.54x);
- `_NUMBER` capped at three digits, so `2280 mm` matched its own tail and became
  28 cm instead of 228 cm — a tenfold error, in the units most non-IKEA
  retailers publish, that sails through the 1–400 cm plausibility gate looking
  like an ordinary piece of furniture;
- the price regex accepted a bare `.` as the amount, so the full stop in
  "…polyurethane foam. SAR 2,495.00" matched first and every price that followed
  prose came back empty.

All three are pinned by regression tests.

**Update from the first live check (real network, this repo unmodified).**
`python -m furn_catalog.diagnose` was run against actual IKEA KSA. Discovery
works: the search API returned real products with correct names and canonical
`/sa/en/` URLs. Dimensions did not: on the pages checked, all six static
extraction layers came back empty, including a whole-page scan that found the
substring `cm` 113 times without one parseable triple among them — independent
confirmation that the measurement panel is client-rendered, not merely
mis-selected. The search API's measurement field was also empty on every
result for the pipeline's own `sofa` query, which falsifies the assumption this
adapter was designed around: `_measure_text` originally only scanned the
product object's own direct string values, not nested ones, and has been
widened to scan recursively as a no-downside hardening — but whether that
recovers anything, or whether the field is simply absent from this endpoint,
is still unconfirmed. `python -m furn_catalog.diagnose --raw sofa` gets the raw
JSON needed to settle it. Until then, the browser-render retry is carrying
IKEA's dimension extraction essentially alone; see "The browser retry" above.
